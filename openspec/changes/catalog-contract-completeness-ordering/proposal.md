## Why

The catalog currently accepts prompt-bearing modes without `after_copy`, treats absent `eval_required` differently from an explicit value without recording the intended policy, and can expose filename order even though `catalog/index.yaml` already declares user-facing prompt order. These ambiguities make valid authoring data capable of producing incomplete cards, inconsistent generated surfaces, and accidental ordering drift.

## What Changes

- Classify every existing mode that lacks `after_copy`, backfill every prompt-bearing mode before enforcement, preserve the exact nonblank `fill_pointer: match_placeholder_table` authority, require mode IDs to be unique within each item, and represent non-paste-path omission as an explicit validated state rather than relying on field absence.
- **BREAKING** Replace optional `eval_required: boolean` with a required explicit evaluation policy and rationale. A `required` policy also owns one or more structured acceptance checks, each discriminated as a command or observable condition, so the release or reliance gate has a deterministic valid shape rather than only descriptive prose.
- **BREAKING** Make unique lane order plus each lane's `prompt_slugs` sequence in `catalog/index.yaml` the sole canonical base order. The loader must validate the complete raw item set before canonicalizing it; empty-query and non-ranking lane, scope, cluster, grouping, and truncation projections must preserve canonical prompt-relative order; explicitly documented relevance or analytical rankings may reorder prompts with canonical rank as their final deterministic tie-breaker; and `featured_prompt_slugs` remains an explicit curated-order/ranking exception whose authored subset sequence is preserved without becoming a second full-catalog authority.
- Define deterministic accessible behavior for a selected no-paste mode on prompt detail and catalog preview surfaces, keep page-level Copy link and Print actions available, require Copy link to copy only the canonical prompt-page URL, remove paste-only controls rather than disabling them, prohibit prompt-body, filled-prompt, and provider-payload clipboard/open side effects, and exercise the behavior through an isolated generated fixture build without adding a sentinel record to production catalog YAML or generated data.
- Add the reviewed replacement evaluation/post-copy data first while retaining legacy fields temporarily in the uncommitted working state, migrate every legacy consumer—including `web/scripts/emit-seo.mjs`, its tests, and the existing Python `eval_required` assertion—and only then remove item-level `order` and `eval_required` in one coordinated lane-owned cutover.
- Preserve the current paired site-data publication transaction and file ownership: `catalog.json` owns full public collections, while `catalog-meta.json` owns compact metadata and `catalog_sha256` rather than duplicate collections. Even when this change lands alone, that digest is lowercase SHA-256 over the exact final `catalog.json` bytes, including the full artifact's schema/version field. Both paired `generated_at` values must be valid and exactly equal before their shared volatility may be ignored; a separately specified source-provenance collection may extend the full bytes without changing the digest algorithm.
- Sequence replacement-data authoring and consumer migration before coordinated legacy-field removal and strict integrated enforcement so no committed state requires a reader to consume a shape it cannot understand.
- Add one executable parity oracle spanning record-item, record-index, package, README artifact/freshness, site-data artifact, SEO/route/discovery/full-Markdown artifact, and mandatory generator-boundary domains. The `parity-oracle` owner owns the shared framework and non-overlapping core cases, while `seo-discovery` is the sole writer of SEO, route/discovery, and full-Markdown parity cases and fixtures, including, when `source-provenance-site-data-bridge` is co-applied, source-aware overlap delegated by that change. Every fixture names the adapters that can enforce its invariant, every named adapter must run, and results must match acceptance plus the complete normalized, deduplicated, deterministically ordered diagnostic set; exact human message prose is contextual rather than a parity key.
- Add positive and negative fixtures for incomplete post-copy metadata, invalid omission states, duplicate mode IDs, invalid fill pointers, ambiguous evaluation policy, unknown or duplicate canonical-order membership, no-paste interaction behavior, invalid or unequal paired timestamps, and generated prompt-order drift.

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

- `prompt-catalog`: Tighten mode completeness and omission semantics, replace ambiguous evaluation metadata, and establish `catalog/index.yaml` lane membership order as the only prompt-order authority.
- `readme-catalog-generate`: Require complete post-copy rendering for paste-path modes and exact Prompt Index and Prompt Library order parity with canonical index order.
- `web-build-assurance`: Require executable validator parity, an isolated no-paste fixture build, and canonical prompt ordering in generated site-data and its non-mutating freshness gate.
- `accessible-catalog-interactions`: Define exact no-paste prompt-detail and preview behavior, control availability, and mode-transition announcements.
- `route-publication-contract`: Migrate SEO and machine-readable discovery output to the explicit evaluation and canonical-order contracts.

## Impact

Affected authoring and validation surfaces include `catalog/items/*.yaml`, `catalog/index.yaml`, both checked catalog fixture trees, `catalog/schema/*.schema.json`, Zod schemas and semantic checks in `packages/catalog-core`, README and paired site-data emitters, `web/scripts/emit-seo.mjs`, route/discovery projections, prompt-detail and preview interactions, SEO and isolated browser-fixture tests, Python README contract checks and their legacy evaluation assertion, executable parity fixtures, generated `README.md`, generated web catalog data, and ephemeral discovery output. The named `seo-discovery` owner is the sole writer of SEO, route/discovery, and full-Markdown parity cases and fixtures; the `parity-oracle` owner supplies the shared framework and non-overlapping core cases, and source provenance delegates source-aware overlap to `seo-discovery`. The named `site-data-integration` owner exclusively owns shared emitter, pair-test, and comparator implementation when this change and `source-provenance-site-data-bridge` are applied together. When applied together, it waits for that change's apply prerequisite and compiled seam before projecting catalog prompts, and final coexistence testing follows that projection; landing alone first, it projects catalog prompts with no source wait. The `generated-publication` owner remains the sole writer that regenerates the checked pair, and, when co-applied, the source change delegates publication to it. This change does not add a taxonomy, route family, compatibility reader, production sentinel prompt, or runtime migration path; the catalog migration and enforcement must land atomically through the existing one-way generators.
